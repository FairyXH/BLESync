# BLESync

BLESync is a conservative Windows LocalSystem service for persisting selected Bluetooth pairing registry state to a shared, non-system storage path. It is intended for two equivalent Windows installations using the same physical Bluetooth adapter.

## Important scope

The implementation intentionally does **not** copy `Enum\\BTH`, `Enum\\BTHENUM`, or `Control\\DeviceClasses`. Those trees contain PnP and interface-instance data generated by the current Windows installation and blindly importing them is unsafe. The primary portable candidates are normalized `BTHPORT\\Parameters\\Devices` and sensitive `BTHPORT\\Parameters\\Keys` data.

Cross-boot restoration of Bluetooth pairing data is inherently Windows-build/driver dependent. Run the differential study in `docs\\BluetoothRegistryAnalysis.md` before enabling restore on a production machine. The service defaults to conservative, user-first behavior and never cycles `bthserv` on a timer.

## Build

Prerequisite: 64-bit MinGW-w64 `g++` in `PATH`.

```bat
build.bat
```

Output: `build\\BLESync.exe` and a copy of `BLESync.ini`.

## Install / uninstall

Run an elevated command prompt, then:

```bat
install.bat
uninstall.bat
```

The controller mode can also be called directly:

```text
BLESync.exe --install
BLESync.exe --uninstall
BLESync.exe --capture
BLESync.exe --console
```

The service name is `BLESync`; display name is `BLESync Bluetooth Persistence Service`. Installation configures LocalSystem, auto-start with delayed start, and service failure recovery with bounded restart delays.

## Configuration

`BLESync.ini` must be beside the executable, regardless of the process working directory:

```ini
[BLESync]
StoragePath=D:\BLESyncData
ScanInterval=5
LogLevel=INFO
```

`ScanInterval` is clamped to a safe minimum of one second. Storage is created if possible. Configuration or storage failures stop synchronization rather than attempting Bluetooth service restarts.

## Storage and security

The service creates:

```text
D:\BLESyncData\
  registry\\devices.regdata
  registry\\keys.regdata
  state\\metadata.ini
  logs\\BLESync.log
```

Files are written using temporary files, flush, backup, and replacement. Snapshot payloads include a SHA-256 digest when the platform crypto provider is available. The storage ACL is restricted to LocalSystem, Built-in Administrators, and the service process owner. Link keys are never logged. Do not place the storage path in a user-shared directory.

## Synchronization policy

- Stable local changes are treated as user changes and are published to storage.
- A valid newer storage snapshot may be restored only when local state is stable and no recent local user change is observed.
- Bluetooth OFF, service pending states, unknown radio state, and unstable PnP state suppress restore.
- Restore uses a generation/hash suppression window and verifies the post-restore snapshot before returning to monitoring.
- Concurrent writers use a named mutex and metadata version/hash. Conflicts are retained in the log as redacted summaries; no secret values are printed.
- The service does not periodically stop/start `bthserv` and does not force Bluetooth ON.

## Testing

Run the static harness after building:

```powershell
powershell -ExecutionPolicy Bypass -File tests\\run_static_tests.ps1
```

Real pairing/removal and two-OS restore tests require an elevated Windows lab with a controllable Bluetooth adapter. The current host's live baseline and limitations are recorded in `docs\\BluetoothRegistryAnalysis.md`.

## Troubleshooting

- Check `StoragePath\\logs\\BLESync.log` and Windows Service Control Manager state.
- If `BTHPORT\\Parameters\\Keys` cannot be opened, verify the service is actually running as LocalSystem; never loosen registry ACLs.
- If the service remains stopped, inspect Event Viewer and validate that `BLESync.ini` is beside the executable.
- If a snapshot is rejected, preserve the existing registry and inspect the hash/format error. Do not manually import arbitrary registry exports.
